# Architecture

## Principles (GDD 10.5)
- Small, focused classes. No giant managers.
- **Gameplay logic is plain C#** wherever possible (no `MonoBehaviour`), so it can be unit-tested without scenes.
  MonoBehaviours are thin adapters: they read input, show things and forward calls.
- **Data vs behaviour:** definitions (items, customers, merchants, dimensions, upgrades) are ScriptableObjects.
  Runtime state (an item in your inventory, a customer in the shop) is a separate plain class.
- **UI never changes game data directly.** It asks a system (e.g. `TradingManager.TrySell(...)`), which validates and
  then raises an event the UI listens to.
- **Events for communication** (`event Action<...>`), not objects searching for each other.
- No third-party dependencies.

## Assemblies

## Build pipeline
The project is built in the cloud by Unity Build Automation from GitHub. Scenes are **generated by code**
(`ProjectSetup`), not committed. Before each build, `CloudBuild.PreExport` creates missing scenes (never
overwrites existing ones), sets Build Settings and Android settings, validates, and throws if anything is wrong.
`MobileInputController` compiles against the Input System only when the package is installed (asmdef
`versionDefines` → `BLACKMARKET_HAS_INPUT_SYSTEM`). Otherwise it uses legacy input.

## Start-up flow
```
App starts
 └─ GameManager.EnsureExists()   [RuntimeInitializeOnLoadMethod, before first scene]
     └─ creates "[GameManager]" (DontDestroyOnLoad)
         ├─ new GameStateManager(Booting)  → ServiceRegistry
         └─ new SceneLoader(host)          → ServiceRegistry
 └─ Bootstrap scene loads
     └─ Bootstrapper.Start() → SceneLoader.LoadScene("Shop")
 └─ Shop scene loads → GameManager.OnSceneLoaded → GameState: Booting → Shop
```
Because the GameManager creates itself, pressing Play in *any* scene works during development.

### Why a ServiceRegistry and not singletons?
The GDD asks to avoid unnecessary singletons. Only `GameManager` is a single persistent object, and it is the
**composition root**: the one place systems are created. Other code gets systems with
`ServiceRegistry.Get<InventoryManager>()`. Tests can register fakes, and the creation order is visible in one method.

## Game states
```
Booting ──► MainMenu ──► Shop ◄──► Traveling ◄──► Marketplace
   └──────────────────────► Shop / Marketplace (dev: Play from any scene)
```
Travel must pass through `Traveling`. Portal effects, autosave and loading screens hook into that moment.
Illegal transitions are refused and logged.

## UI approach
UI is built in code (`UIFactory`) from one design system (`UITheme`): dark walnut panels, thin brass borders,
parchment text, flat colours, square corners, 1920×1080 reference scaled by height, touch targets ≥140 px tall,
and everything inside the phone's safe area. Screens only display data and raise events. Controllers such as
`ShopSceneController` connect them to gameplay.

## Generated scenes
Scenes containing a `__GeneratedByProjectSetup` object are rebuilt from code on every cloud build
(`ShopSceneBuilder`), so layout changes ship by pushing code. Scenes made by hand (no marker) are never overwritten.

## Key rules for upcoming systems
- **Transactions are atomic:** validate everything (money, stock, capacity, item still exists) first, then apply
  money and inventory changes together. If any check fails, nothing changes. A transaction ID / "in progress" flag
  blocks repeated button presses.
- **Money is an integer** (`long` coins). No floating-point currency.
- **Negotiation and pricing are deterministic** given the inputs (personality, value, offer). Any randomness uses a
  seeded random source passed in, so tests are repeatable.
- **Saves:** versioned JSON in `Application.persistentDataPath`. Write to a temp file, validate it, then replace the
  old save and keep one backup. A corrupt or missing save never overwrites a valid one.

## Naming
- Namespaces: `BlackMarket.<Folder>` (e.g. `BlackMarket.Core`).
- Private fields `camelCase`, properties/methods `PascalCase`, serialized fields `[SerializeField] private`.
- Placeholder scene objects start with `PH_`.
